# VRCX-K 开发路线图（概览）

> **本文件 = 里程碑级概览**（落 M/F 阶段粒度）。开发阶段的**任务级细化**在 GitHub issue 逐层派生（总览 → M/F 总览 → subissue），不在本文件锁死。
> 两条线分列：**基建线 M0-M5**（平台能力，对齐架构 §4.1）+ **功能线 F1-F5**（VRCX 复刻，产品主线，§2）。功能插件清单到对应 F 开发阶段细化定稿。

## 0. 项目目标（双线）

- **平台**：Cordis + Tauri + React，社区插件生态（架构 v4.2 定稿）。
- **产品（主线）**：把 VRCX 能力**完整复刻**为官方维护的 **base 插件包**——登录/WS、数据库引擎、好友列表、位置变更、通知、Feed 等子插件，跑在 Cordis 宿主上。
- **双线关系**：基建线铺路（宿主/壳/插件机制）；功能线逐块搬入 VRCX 能力成 Cordis 插件。功能线是用户可见主线，基建线是支撑。
- **终态**：base 包稳定后开放社区市场，垂直功能由社区插件承接（架构 §4.7 第三档）。

## 2. 功能线（产品主线）：VRCX 复刻 F1-F5

> 每个 F = 一段可验收的 VRCX 复刻交付，范围含「做 / 不做 / 观望 / 交社区」显式边界（§2.1）。具体插件拆分（coordinator 粒度，见 §3）到 F 开工时在 GitHub issue 细化。

| F | 名称 | 范围（做） | 不做/观望/社区（显式） | 依赖基建 | 验收 |
|---|---|---|---|---|---|
| **F1** | 账户与连接地基 | 登录(含 2FA)、token/凭证管理、WS 长连、数据引擎(SQLite/schema/迁移) | — | M1 壳跑通（host 可 spawn） | 能登录、WS 收事件、数据落库 |
| **F2** | 好友/社交核心 | 好友同步/关系/状态追踪、位置、世界/Avatar 信息、备注、收藏 | — | F1 + M2（插件 SDK v0） | 好友列表+实时状态+位置历史可查 |
| **F3** | 动态与通知 | Feed/GameLog、用户事件历史、通知收发业务、实例 stats | 桌面通知只发业务事件（弹窗=双手，非插件） | F1/F2 + 壳通知能力 | Feed 正确、通知业务闭环 |
| **F4** | 界面与查询 | Dashboard widgets、Heatmap、搜索、状态预设、导出导入、服务器监控 | — | M3（前端扩展契约） | UI 插件示例 + 搜索/导出可用 |
| **F5** | 完整性与收尾 | VRCX 核心复刻收尾、跨版本数据合并(DBMerger 移植)、全量回归 | 边缘功能归位（见 §2.1） | M4/M5 | 核心 100% 复刻，边缘按 §2.1 归位 |

### 2.1 「做不做」显式边界（对齐 §3 归属分类）

| 能力 | 决定 | 触发/形态 |
|---|---|---|
| VR Overlay | **观望**（官方暂不下场） | 有用户基础+反馈后单独立项；届时 T2 dll 插件（架构 §1.4 C 类 runner 已预留） |
| 截图数据嵌入 | **独立插件**（非 base 日常核心） | 官方可单独立项 or 社区；不进 F 主序列 |
| 内嵌浏览器(Cef) | **双手开窗替代** | 直接 call Tauri 开外部网页/窗口，宿主/Cordis 不涉及 |
| Discord Rich Presence 等平台桥 | **交社区** | 官方明确不做；第三方垂直功能样板 |
| 桌面通知弹窗 | **双手承接** | 宿主只发业务事件；弹窗= Rust 原生通知 |
| 进程注入/读游戏内存/Unity 内 UI | **禁区**（官方不背书） | VRCX 自身不做；ToS 风险；社区做也不背书（架构 R3） |

> 各 F 开工时若出现新的「做不做」点，在该 F 的 GitHub issue 记录并回填本表。

## 3. 功能线方向：base 插件包拆分原则（预演）

> ⚠ **只锚定粒度与分类原则，不落具体插件清单**。base 包拆哪些插件、每个多细，留到对应 F 开发阶段按真实依赖/服务边界细化定稿；此处仅给方向。

**插件粒度原则**：base 插件粒度 ≈ **服务/协调器边界**（参照 VRCX 官方 coordinator 层：friendPresence / friendRelationship / friendSync / location / world / avatar / instance / invite / memo / gameLog… 一域一协调器），而非 UI 功能域；共享横切（DB 引擎 / HTTP-API 客户端 / WS 长连 / GameLog 读取 / 搜索索引）作被依赖基座。**具体拆分与取舍开发阶段定稿，本文件不预锁。**

### 4.1 移动端（Android/iOS）：**不是"把桌面 sidecar 移植过去"**

2026-09-11 调研结论见 [`mobile-feasibility.md`](mobile-feasibility.md)。三条要点，避免按错误前提估工：

- **桌面"壳 spawn 常驻 host 进程"不能照搬**。Android 侧 `execve` 受 SELinux `neverallow` 限制（targetSdk ≥ 29），Tauri 自身也**不打包、不启动**移动端 sidecar（`tauri-plugin-shell` Android 仅 `level="partial"`）。
- **但并非不可能**，且三道墙中只有一道是硬的：Play 政策墙因**我们只在 GitHub 分发**而不适用；"常驻"墙因**按需唤醒**而软化；`targetSdk ≤ 28` 可落进被显式豁免的 SELinux 域（Termux 同款机制，**有长期风险**）；真正硬的只有 **bun 自身 Android 产物的稳定性**。
- **移动端与桌面是"同契约、另一套实现"**，不是移植；且**"保 kkrpc 契约"≠"保 Cordis/JS 插件生态"** —— 后者决定移动端要不要内嵌 JS 引擎。**未立项**。


## 5. 协作约定

- **概览 ↔ 细化的分工**：本文件只回答「现在到哪个 M/F、base 包往哪个方向」；「这个阶段具体做哪几个任务、验收什么」在 GitHub M/F 总览 issue，开工即细化并派生 subissue。
- **每阶段开工动作**：新建 M/F 总览 issue → 拆任务 subissue（含验收/依赖）→ 实现 → 勾选回填（GitHub task list 引用）。
- **「做不做」纪律**：新能力先按 §2.1 归类（做/观望/社区/禁区），再进 F 范围；不归类的功能不承诺。
- **保持预演**：功能线分类与粒度是方向，进开发阶段按当时架构/生态重估，不教条。
- **风险/上游**：架构 §4.2 风险 + §4.5 上游追踪（bun#35690 等），每里程碑复核。
