# 宿主：会话与设备管理（需求记录）

> 状态：**需求记录，未排期、未立项**。本文只回答"缺什么、为什么缺、将来集成在哪"，**不含实现设计**。
> 日期：2026-09-11。所有"现状"均标注代码位置，可复核。

## 0. 一句话

桌面首版是**事实上的单客户端**设计：它服务恰好一个运行在本机的脸。这没有错——首版的目标就是它——但**没有任何一处能推广到"多设备"**。本文把这个隐含假设显式写出来，并记录要变成多客户端时缺什么。

关联：`architecture-proposal.md` **§4.8**（多客户端期权，当前决策"不实现"）、`mobile-feasibility.md`（移动端 = 第三端，§2.1/§7 的配对与鉴权需求）。本文是那两处所指的**宿主侧对应物**。

## 1. 现状（代码事实）

| 维度 | 现状 | 位置 |
|---|---|---|
| 凭据 | **每次启动随机生成一个 32 字节 hex token** | `host/src/ws.ts:15` |
| 校验点 | 唯一 choke point：连接时比对 query 里的 token，不符即 `close(1008)` | `host/src/ws.ts:30-38` |
| 监听端点 | **硬编码** `host:"127.0.0.1"`、`port:0`（随机端口） | `host/src/ws.ts:16` |
| 凭据交付 | `ready{port,token}` → stdio → 壳 → Tauri IPC → 脸 | `host/src/index.ts:238-243`、`src/App.tsx:120,126` |
| 脸侧 URL | **硬编码** `ws://127.0.0.1:${port}?token=${token}` | `src/host.ts:15` |
| 多连接 | 服务端按 `connection` 逐个 `expose()`，**技术上能多连** | `host/src/ws.ts:30-38` |
| 会话身份 | **无**——不区分、不记录连上来的是谁 | — |
| 广播（宿主→脸） | **无**——ws 层暴露给脸的只有 `ping` / `getVersion` | `src/host.ts:9-12` |
| 吊销 / 轮换 / 超时 / 连接上限 | **无** | — |
| 分级授权 | **无**——token 全有或全无 | — |
| 重连 | **脸侧有**（generation 幂等重连 + `host-ready` 重挂） | `src/App.tsx` |

### 1.1 一条关键推论（影响将来设计）

端口是 `port: 0`（随机）、token 是每次启动随机 —— **两者都在每次宿主启动时重新生成**。因此：

> **任何"持久的每设备凭据"都必须独立于这个每次启动的 token 存在。**

宿主重启（含 **51 重启**）会换掉端口与 token，所以持久凭据**不能**建立在它们之上。这条不是推测：`listenHostWs` 每次调用都新生成 token，而 51 重启会让宿主重新走一遍启动。脸的 generation 幂等重连解决的正是"宿主换了端口"，但它复用的是**当次**交付的新凭据——这在单客户端下够用，在多设备下正是要重新设计的地方。

## 2. 需要什么（逐条）

1. **会话身份**：设备 id / 标签 / 平台 / 连接时间；一张活会话表。
2. **凭据生命周期**：配对（带外用户确认）→ 每设备长期凭据 → 轮换 → 吊销。**当次 token 无法承担此任**（见 §1.1，且它是经本机 IPC 交付的，只在 localhost 前提下安全）。
3. **传输绑定**：`127.0.0.1` 需可配置 + `wss://`（TLS）。明文 `ws` 只对 localhost 成立。
4. **分级授权**：不是每台设备都该拿到全部能力（可信桌面 vs 手机 vs Web 客户端）。现在 token 是**全有或全无**。
5. **广播**：业务事件推给全部/部分会话 —— 这是 ws 层**缺失的宿主→脸方向**。
6. **生命周期策略**：踢下线、连接数上限、空闲/断连处理、重连语义的宿主侧对应物（脸侧已有）。
7. **可观测**：哪台设备做了什么（审计），以及把"当前 N 台设备已连接"暴露给 UI。

---

## 3. 集成点：这是"加一个服务"，不是"加一套机制"

**这是本文最重要的结论。** 上表每一项都能挂到**已存在**的结构上，不需要发明新框架：

| 需要的能力 | 已有的落点 |
|---|---|
| 凭据校验 | `host/src/ws.ts:32` —— **唯一 choke point**，换掉这一处判断即可 |
| 服务形态 | Cordis 服务范式：`declare module "cordis" { interface Context { tray: TrayService } }`（`host/src/tray.ts:26-30`）+ `attachShell(...)` 装配（`host/src/index.ts:238-254`）→ `ctx.sessions` 照抄此形状 |
| 多订阅者分发 | `fanout<T>()`（`host/src/stdio.ts`）已是现成范式，广播可复用其形状 |
| 线协议测试 | `host/tests/{shortcut,tray}-wire.test.ts` 的 **in-memory transport** 打法可直接沿用 |
| 传输抽象 | 壳侧 `kkrpc_peer` 已泛化（`src-tauri/src/kkrpc_peer.rs`）——同为"不把传输焊死"的思路 |

也就是说：**扩展点数量是 1 个服务 + 1 处校验替换**，不是 N 个新机制。这也符合"宿主是插件宿主"的定位——**连接/设备/会话天生属于服务层，不该往核心里塞机制**。

## 4. 与既有权衡的关系

- `architecture-proposal.md` **§4.8** 把多客户端记为选 `kkrpc/ws` 而非 Tauri 私有 IPC 的**期权价值**，并明确"**当前决策：不实现**"，且预告了缺口：*"需补「外部访问鉴权 + 端口暴露安全模型」，属独立立项"*。**本文就是那份缺口的宿主侧清单。**
- **L2/L3**（移动推送 + 服务器）=**独立架构立项，现在不写认知架构**。会话管理落在这里，因此本文同样**只记需求，不给实现**。
- `mobile-feasibility.md` §2.1 列了脸侧端点可配置 + TLS + 配对、§7 把"配对与鉴权"列为待决。**手机只是第一个真正的第二客户端**，但需求不止于移动端（Web 客户端、第二窗口同理）。

## 5. 待决问题（立项时先答）

1. **凭据模型**：每设备密钥 / 用户账号 / 两者兼有？与 VRCX 自身的账号体系是什么关系（若有）？
2. **配对状态存哪**：宿主磁盘 / 壳 / 将来的服务器？§1.1 的推论要求它独立于每次启动的 token。
3. **核心服务还是插件**：`ctx.sessions` 需要被 `ws.ts` 咨询，倾向核心侧；但**授权政策**（谁能做什么）更适合插件化。
4. **信任分级**：手机是"同一用户、较低信任"还是"同等信任"？这决定 §2.4 的粒度。
5. **与 51 重启 / generation 的关系**：重启后会话如何重建、要不要通知对端"宿主换代了"。

## 6. 明确不在范围

按 §4.8 与 L2/L3 的既有决策：**现在不实现、不写认知架构、不排期**。本文的作用是**避免将来从错误前提出发**——例如误以为现在的 token 机制稍加扩展就能多设备，或误以为需要新建一套鉴权框架。
