## 0. 为什么复核

captain 先前的判断是：

> 「SQLite 单文件单连接，没有 PG 的池化断裂问题 ⇒ 不需要那套事务复杂度。」

t2 的结论是：

> `_txTail` 串行队列 —— **[SQLite 真实需要]**：单连接模式下**两事务并存打到同一连接会损坏连接**。

**两者冲突，且直接决定我们的数据层要不要做串行化**，所以必须实测。

---

## 1. ✅ t2 是对的：并发事务在单连接上是真问题

实测（`.temp/probe-sqlite-concurrency.ts`，bun:sqlite）：

| 测试 | 结果 |
|---|---|
| 嵌套 `BEGIN` | ❌ `cannot start a transaction within a transaction` |
| **bun 的 `db.transaction()` 重入** | ✅ **自动用 savepoint**（inner 正常返回，不报错） |
| **两个并发异步事务** | ⚠️ **灾难**（详见下） |
| 双连接并发写（有 `busy_timeout=5000`） | ❌ `database is locked` |
| 嵌套错误后连接是否可用 | ✅ 可用（回滚后可继续写） |

**并发异步事务的实测输出**：

```json
{ "log": ["A:began"],
  "error": "cannot start a transaction within a transaction",
  "rows": ["A-1"] }
```

**读法**：A 先 `BEGIN` 并插入一行，`await` 期间 B 也 `BEGIN` → **抛错** → `Promise.all` 整体失败 →
**A 永远走不到 `COMMIT`** ⇒ 只留下 `A-1`，**连接被留在打开的事务里**。

⇒ **这确认了 t2 的判断**：不是"池化才有的问题"，**单连接 + 并发异步 = 真问题**。
⇒ 而我们的宿主是 **事件驱动的异步运行时**，"并发"是常态而非例外。

**但注意一个前提**：bun 的 `db.transaction()` 是**同步**的，正常用它不会撞这个坑（它自动用 savepoint 处理重入）。
⇒ **触发条件是「手动 BEGIN/COMMIT 且中间有 await」**。

---

## 2. ⚠ 但 `busy_timeout` 有一个陷阱（captain 新增发现）

`.temp/probe-lock-upgrade.ts` 实测三种开事务方式在**锁被他人持有**时的行为：

| 方式 | 等待时长 | 结果 |
|---|---|---|
| **先写**（`BEGIN` 后直接 `INSERT`） | **2241 ms** | ✅ **遵守了 busy_timeout**（等满才失败） |
| `BEGIN IMMEDIATE` | 2227 ms | ✅ 遵守 |
| **先读后写**（`BEGIN` → `SELECT` → `INSERT`） | **1 ms** | ❌ **完全绕过 busy_timeout，立即失败** |

**解释**：先读会拿 **SHARED 锁**，再升级为写锁时 SQLite **不能安全等待**（等待会死锁）⇒ **立即返回 `SQLITE_BUSY`**。

> ⚠ 读数说明：A 与 B 在**同一线程**，`bSequence` 是同步的 ⇒ A 的释放定时器**无法在 B 阻塞期间触发**，
> 所以 B **必然**耗满超时。这里的数字**只说明"busy_timeout 有没有被咨询"**：
> ~2200ms = 等了（超时被尊重）；~0ms = 没等（超时被绕过）。

### 对我们的含义（**待验证，未定论**）

若数据层出现「**同一事务内先 SELECT 再写**」的模式，在竞争下会**立即失败**，而配置的 `busy_timeout` 形同虚设。

**候选对策**（**尚未验证**，属上报的经验点）：

1. 写事务一律用 `BEGIN IMMEDIATE`（**提前**拿写锁，避免升级）
2. 或：写事务内**不先读**（把读放到事务外）
3. 或：应用层串行化所有写（与 t2 的 `_txTail` 思路一致）

## 3. 与 captain 先前结论的关系（**修正**）

captain 曾在 #27 上建议「写即提交、不做事务机制」。**本次实测要求修正该表述的边界**：

| 原表述 | 修正 |
|---|---|
| 「写即提交，不需要事务机制」 | 对**单条写**成立（`db.run()` 返回即落盘） |
| 「SQLite 单连接没有并发问题」 | ❌ **错**。单连接 + 并发异步 = 真问题 |
| — | **新增要求**：写路径必须有**串行化**（或保证不同时开两个事务） |

⇒ **"直接写"依然是对的**（简单、低耗），但它**隐含一个前提**：
**同一时刻只有一个写事务在飞**。这个前提**需要代码保证**，不是自动成立的。

## 4. 供 t6 汇总者采纳的经验点

```
### 经验点（队长复核）：单连接的并发事务必须串行化
- 解决什么问题：单连接下两个异步事务交错 => 第二个 BEGIN 抛错，第一个永不 COMMIT，
  连接被留在打开的事务里（实测：rows 只有 ["A-1"]）。
- 方案：应用层串行化写事务（t2 的 _txTail 思路），或用同步的 db.transaction() 避开手动 BEGIN。
- 代价/陷阱：bun 的 db.transaction() 是同步的，无法在事务中间 await；
  一旦手写 BEGIN/COMMIT 且中间有 await，就必须自己保证不并发。
- 证据：.temp/probe-sqlite-concurrency.ts 原始输出。
- 与我们的差异：我们的宿主是事件驱动异步运行时，"并发"是常态，比旧实现更需要这条。
```

```
### 经验点（队长复核）：busy_timeout 在锁升级场景被绕过
- 解决什么问题：先读后写会让 deferred 事务从 SHARED 升级到写锁，SQLite 不能安全等待，
  直接返回 SQLITE_BUSY，busy_timeout 完全不生效。
- 方案：写事务用 BEGIN IMMEDIATE 提前拿写锁；或事务内不先读；或应用层串行化。
- 代价/陷阱：只有"先读后写"会中招，纯写事务正常等待（实测 2241ms vs 1ms）。
- 证据：.temp/probe-lock-upgrade.ts 原始输出。
- 与我们的差异：待验证——我们尚未设计具体的写路径，此点作为**设计约束**上报。
```

## 5. 无法确定的事项

1. **`BEGIN IMMEDIATE` 在真实竞争下是否确实更优**——本次测试中 A 持有锁不放，B 必然超时，
   无法体现"B 提前拿锁因此排在前面"。需要**异步/多进程**的测试才能验证。
2. **t2 说的"损坏连接"具体是什么表现**——本次实测表现为"连接留在打开的事务里"（可回滚恢复），
   未见永久性损坏。**可能与旧实现的 C# 桥层有关，不适用于 bun:sqlite。**
3. 与 t2 报告 §并发写测试（`node:sqlite` + worker_threads）的结论是否一致——**未交叉验证**。
